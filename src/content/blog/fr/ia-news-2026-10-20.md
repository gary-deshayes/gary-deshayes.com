Le **19 octobre 2026**, AWS a annoncé **TorchNeuron**, un backend PyTorch natif pour ses puces **Trainium2 et Trainium3**. Le code passe open source en **Apache 2.0** au PyTorch Conference North America de San Jose, le **20 octobre**, en beta publique. Dépôt : `github.com/aws-neuron/torch-neuronx`.

L'argument tient en une ligne :

```python
model = MyModel().to('neuron')   # le seul changement
```

Pas de réécriture, pas de fork du trainer. Pour du code compilé, il faut nommer le backend une fois : `torch.compiler.set_default_backend("neuron")`, puis `model.compile()` fonctionne sans argument.

## Ce qui change sous le capot

Jusqu'ici, Trainium se programmait via **torch-neuronx**, construit sur **PyTorch/XLA**. Ce chemin imposait un graphe compilé, des shapes statiques, et de la recompilation à chaque graph break. TorchNeuron jette XLA et s'enregistre via **PrivateUse1**, le point d'extension officiel de PyTorch pour le matériel custom, avec les API `torch.accelerator`.

Conséquence : `torch.nn`, `torch.tensor`, `torch.autocast`, `torch.distributed` et `torch.profiler` marchent tels quels sur le device `neuron`. Eager mode avec prints et breakpoints pour le debug, `torch.compile` pour la prod (FX graph → Torch-MLIR → StableHLO → fichier NEFF), et **NKI** pour écrire des kernels maison — `NKI-lib` est publié open source avec FlashAttention et des kernels MoE blockwise.

Côté distribué, c'est le vrai déblocage : **DDP, FSDP2, SimpleFSDP, tensor parallelism, pipeline parallelism, DTensor et DeviceMesh** passent sans plomberie spécifique. Les collectifs utilisent les cores dédiés intra-node et l'EFA inter-node, sans changer l'API.

Hugging Face a suivi le même jour : Transformers, Diffusers, Accelerate, PEFT et TRL tournent directement sur Trainium, et HF recommande d'abandonner Optimum Neuron. Le chiffre qui compte : **89 % des 100 architectures de génération de texte les plus utilisées passent out of the box, contre 46 % avec Optimum Neuron v0.4.5**.

## Les limites, à lire avant de migrer

La beta a des trous, assumés dans le billet PyTorch. Sur les suites de tests upstream (ATen, Dynamo, distributed, profiler), environ **154 000 résultats** au run d'août 2026, dont **~69 000 skippés**. Environ 30 000 le sont par les contrôles d'éligibilité de PyTorch (tests CUDA-only, CPU-only) et ne concernent pas Neuron. Restent **~39 000 skips volontaires**, dont **~22 000** pour des opérateurs sans lowering natif — cas limites d'elementwise, reduction, foreach, advanced indexing, linalg avancée, cellules LSTM/GRU fusionnées.

Sont explicitement hors périmètre de cette première version : **shapes dynamiques et symboliques**, tenseurs sparse, NestedTensor, autograd forward-mode (JVP), masques d'attention arbitraires dans le MHA natif (no-mask et causal sont couverts), quantification per-channel. FP8 et TorchAO sont en beta privée, annoncés GA à la prochaine release.

## Pourquoi c'est important pour les devs

Le coût réel d'un modèle n'est pas le prix de la puce, c'est le temps d'ingénieur pour y porter le code. Un backend natif transforme une migration de plusieurs mois en un flag de device, et rend l'arbitrage Nvidia / Trainium testable sur un vrai benchmark.

Pour le web, l'effet est indirect mais réel : l'inférence LLM devient une variable d'infrastructure interchangeable. AWS affirme qu'un même parc sert l'entraînement et l'inférence, et cite Deepgram à **+70 % d'audio traité par dollar**. Chiffres éditeurs, à revérifier sur votre workload.

Le vrai signal, c'est l'engagement d'AWS à **contribuer en amont dans PyTorch** le code qui lie le framework à un fabricant précis. Si ça aboutit, le lock-in CUDA recule pour tout le monde, pas seulement pour les clients Trainium.
